Training a 421M Decision Model on One Laptop

How I built Nirnaya-Flash from a pretrained ModernBERT encoder, what failed along the way, and what 46 experiments taught me about data composition, catastrophic forgetting, measurement noise, calibration, and inference engineering.

Built on Apple M5 Pro · 24 GB unified memory MLX + PyTorch Apache-2.0 release

I built this model alone, on my personal laptop. There was no training cluster, dedicated research team, or large experimental budget behind it.

Most of the project came from continuously reading open-source implementations, papers, model documentation, training recipes, benchmark code, and prior work—then testing which of those ideas actually transferred to the problem in front of me.

0.054calibrated ECE

Training the model was not the hardest part. The harder part was figuring out why one run was genuinely better than another.

Across 46 experiments, I tried partial fine-tuning, sequential curricula, joint training, specialist stages, different objectives, multiple random seeds, probability calibration, and several approaches to preserving capabilities during full fine-tuning. Some ideas worked. Several reasonable ideas failed badly. And some apparent improvements disappeared once I looked more carefully at variance and measurement resolution.

If the evaluation cannot resolve the size of an improvement, the improvement is not evidence.
Problem framing

First: what exactly is a decision model?

Most language-model APIs generate text. But many production systems eventually need something much simpler: make a constrained decision.

{
  "state": "Checkout has been failing for every customer for the last hour.",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments",
        "technical": "Outages and errors",
        "sales": "Plans"
      }
    },
    "urgent": {
      "type": "noul",
      "instructions": "Is this urgent?"
    }
  }
}

For team, I do not need a generated explanation. I want a bounded distribution:

billing      0.01
technical    0.98
sales        0.01

Nirnaya-Flash supports three primitives: Choice for one-of-N decisions, Noul for binary yes/no decisions, and Score for ordinal scales. Probability is part of the interface rather than metadata added afterward.

Evaluation contract

What I was optimizing

Accuracy was necessary, but not sufficient. For the workload I had in mind, I wanted four properties to hold at the same time:

  • Accuracy — the correct answer should win.
  • Calibrated confidence — a 0.9 probability should mean something operationally.
  • Option-order robustness — reordering candidates should not arbitrarily change the answer.
  • Low, predictable latency — this model is intended for synchronous decision paths.
accuracy       argmax prediction equals gold label
ECE            expected calibration error, 15 bins
hard Brier     sum over classes of (p_k - y_k)^2
teacher Brier  Brier score against reference distribution
flip rate      Choice argmax changes when options are permuted
coverage@0.90  share answered with confidence >= 0.90,
               always paired with accuracy on that subset

The target corpus was split by role rather than convenience.

SplitCasesDecisionsPurpose
Train9004,500Model training
TD-DEV180900Reusable research selection
TD-CAL60300Calibration only
Sealed test4002,000One confirmatory evaluation

I used Open-Jev, Banking77, BoolQ, and UltraFeedback as foundation sources, then GoEmotions, News Category, and prompt-injection examples in the specialist stage. Every build was deterministic, leakage-checked, and SHA-256 bound to its run so that a changed metric could be traced back to a changed artifact.

Model design

The architecture

Nirnaya-Flash starts from a pretrained ModernBERT-large backbone. I did not pretrain a language model from random initialization; I adapted a pinned open-source encoder and trained newly initialized decision layers around it.

The model has four parts: the ModernBERT backbone, a primitive embedding, two pre-norm decision-transformer layers with GELU, and a shared marker head that scores each candidate's hidden state.

PropertyValue
Parameters421M
Context limit512 tokens
Question/options reservationUp to 192 tokens
Inference precisionfloat16
Weight size~0.8 GB
Peak inference memory~1.9–2.6 GB

The trade-off: this model is a strong classifier over request-time schemas. It is not intended to be a general-purpose reasoning model.

Experiment 1

How much of the encoder should I fine-tune?

Open-source fine-tuning work gives you many plausible choices: train only the head, unfreeze a few top layers, unfreeze more of the backbone, or fully fine-tune. I tested all four from the same pretrained starting point.

Trainable componentParametersPrimitive macro scoreNoul macro F1
Head only28M0.6430.391
Top 4 layers77M0.7050.448
Top 8 layers126M0.7870.594
Full encoder423M0.8900.791

Full adaptation won on every metric. The largest jump was yes/no: Noul macro F1 nearly doubled from 0.391 to 0.791. For this problem, the representation itself needed to move.

Making full fine-tuning practical

On a 24 GB M5 Pro, memory and step time immediately became first-class constraints. I compiled the forward pass, backward pass, clipping, and AdamW update into one MLX graph.

MetricBeforeAfter
Step time0.354 s0.156 s
Peak memory12.89 GB8.30 GB

I also measured sequence lengths rather than guessing. 99.25% of rows fit inside 384 tokens. A 4,096-token budget peaked at 22.8 GB and collapsed throughput, while the smaller measured budget stayed comfortably within the machine.

Measure the actual sequence-length distribution before deciding how much context to allocate.
Experiment 2

Benchmark performance did not transfer

Early checkpoints reached roughly 98–99% on Banking77 validation and around 80% on BoolQ. A model from the same training family reached only 32.7% on real workflow decisions.

That gap reset my assumptions. The public datasets were useful as supporting skills, but they were not good proxies for the target distribution. From this point onward, the target task drove selection.

Experiment 3

My biggest gain also destroyed the model

The next curriculum was sequential: foundation skills first, then Open-Jev, then specialist data. It sounded reasonable. It also produced one of the most useful failures in the entire project.

With full fine-tuning and no replay, the optimizer has no reason to preserve a distribution that disappears from the gradient stream. The specialist stage inherited that damage and reached only 0.720 on its validation role.

If the final model needs several capabilities, those capabilities must remain visible during optimization.
Experiment 4

A 0.67-point “improvement” that was not actually an improvement

Two specialist recipes differed by 0.67 percentage points on 900 validation decisions. The obvious temptation was to declare a winner.

But the 900 decisions came from only 180 cases, with five correlated decisions per case. Treating the rows as independent would make the confidence interval too optimistic.

SE = sqrt(p(1 - p) / n)
     * sqrt(1 + (m - 1) * rho)

n   = number of decisions
m   = decisions per case = 5
rho = measured intra-case correlation = 0.18–0.21
SplitCasesDecisions95% CI half-width near p=0.75
Small validation60300±6.2 pts
TD-DEV180900±3.6 pts
Sealed test4002,000±2.3 pts
Open-Jev validation4123,419±1.8 pts

The apparent 0.67-point gain sat entirely inside the resolution of the development set. From then on, I compared candidates on identical examples, resampled cases rather than rows, and reported the interval of the paired difference.

Experiment 5

The project changed when I started treating compute like an experimental budget

Data composition had moved performance by tens of points. Many recipe tweaks moved it by less than one. That effect-size mismatch changed how I used the remaining compute.

I separated work into a research lane and a confirmation lane. Research could reuse TD-DEV and inspect anything useful. Confirmation froze the model hash, calibration hash, metric code, bootstrap seed, interval method, and pass criteria before touching the sealed test.

I also started declaring every run before launch: the question, the one changed factor, the expected effect, the stop condition, and the compute estimate. If a run changed several meaningful variables, it stopped being interpretable.

Experiment 6

The highest-information “experiment” used almost no training compute

A read-only diagnostic pass found four issues that changed my conclusions.

Dropout was active during validation

Metrics were stochastic. Fixing evaluation mode reversed two earlier model selections. Evaluation now fails if the model is in training mode, a requested metric is missing, or prediction and label counts differ.

The input formatter had three defects

I found a leading-space tokenization boundary issue around option text, incorrect default yes/no descriptions, and an allocation problem in the question/options token budget. Earlier affected metrics were marked potentially invalid.

One external comparison was contaminated

An apparent gap disappeared after I found my validation examples in the other model's training data. The rule became simple: compare out-of-sample results only with other out-of-sample results.

Trivial baselines anchored everything else

TD-DEV majority-class accuracy   0.483
TD-DEV frozen-backbone accuracy  0.283

Experiment 8

Two reasonable objective changes completely broke training

Once J3 was stable, I tested two ideas that sounded reasonable on paper.

Permutation consistency loss

Typed-decision accuracy fell 21 points, Open-Jev fell 11, and Banking77 fell 9.5.

Hard/soft cross-entropy blending

Accuracy fell to 0.506 after one epoch, below the pre-declared 0.60 abort floor.

The consistency-loss gradient averaged only 0.7% of the task gradient, so its magnitude did not explain the collapse. Gradient clipping did.

mean task gradient norm   7.43
95th percentile           16.47
clip threshold             1.0

Nearly every step was clipped. In that regime, update magnitude is dominated by the threshold, and relatively small auxiliary terms can rotate the update direction enough to alter the trajectory.

Learning: log gradient norms against the clip threshold. A clipping-dominated training regime can be much more fragile to objective perturbations than the auxiliary loss magnitude suggests.

Experiment 9

Was the model under-trained—or had I hit a ceiling?

held-out accuracy               69–74%
training accuracy               74.6% → 83.2%
three-seed probability ensemble 73.8%
all three seeds agree but wrong 19% of those cases

Those numbers did not look like ordinary under-training, so I inspected 240 J3 errors.

Some decisions were genuinely ambiguous

About 60% of TD-DEV examples had less than 0.70 reference probability on the gold answer. Accuracy rose from 0.589 below 0.55 reference mass to 0.888 at 0.85 or higher. Among errors, 80% predicted the reference distribution's second choice.

Other failures were genuine capability gaps

For numeric questions like “does this invoice match the purchase order?”, accuracy was 0.622 even though the reference labels put 0.875 probability on the gold answer on average. Those rows were not primarily ambiguous—the model was weak at comparing numbers embedded in the state.

Experiment 10

I tried adding NLI data. It made the target task worse.

I had seen natural-language inference used successfully across many transfer-learning settings, so I tested whether SNLI and MultiNLI would improve binary decisions.

BoolQ improved. Open-Jev improved. Typed-decision accuracy fell 3.7 points, with a paired 95% CI of −6.4 to −0.9.

A dataset can look semantically related to the skill you want and still be distributionally wrong for the target task.

Experiment 12

The strongest model was one I could not release

A broader specialist, S2, became the strongest checkpoint, but some of its data was non-commercial or had unclear licensing terms. That conflicted with my goal of an Apache-2.0 release.

I replaced those sources with permissively licensed stand-ins and trained S3.

On the target task, S3 remained statistically consistent with S1: −0.4 points with a 95% CI of −3.0 to +2.1. Its three seeds were 0.787, 0.779, and 0.799. I froze 0.787 because it was the median, not the maximum.

The recipe that survived

The final training strategy

adaptation        full fine-tuning of encoder + decision layers
optimizer         AdamW
weight decay      0.01
learning rates    encoder 2.5e-5 · decision layers 1e-4
schedule          6% warmup · cosine decay to 1e-6
clipping          global norm 1.0
batching          microbatch 8 × accumulation 8 = effective batch 64
token budget      <= 1,024 tokens per microbatch
loss              soft-target CE + 0.1 × Brier
augmentation      Choice options re-permuted every epoch
mixing invariant  source quotas within each accumulation window ±5%
selection         TD-DEV accuracy after every epoch

None of those settings is especially exotic. The largest gains came from the structure of the training data and the experiment design, not from discovering an unusual optimizer.

Probability quality

Calibration was a separate development stage

For a decision model, probabilities are part of the API. I therefore gave calibration its own data, parameters, artifact, and hash rather than treating it as reporting polish.

Unconstrained per-primitive temperatures were below 1:

Choice  0.60
Noul    0.39
Score   0.41

Since temperature scaling uses z / T, values below one sharpen the distribution. The raw model was underconfident, which is consistent with soft-target training on ambiguous supervision.

A trade-off between ECE and teacher Brier

With only 300 calibration decisions, I shrank each fitted log-temperature toward zero. The shrinkage strength was chosen by a pre-declared rule that required both ECE and teacher Brier to remain below 0.10.

AlphaECETeacher BrierCoverage @ 0.90
0.00.1460.0570.103
0.30.1060.0660.143
0.50.0700.0780.180
0.80.0540.1020.253
1.00.0530.1210.330

The full fit minimized ECE but violated the teacher-Brier target. Alpha 0.5 satisfied both. The selected temperatures were Choice 0.78, Noul 0.62, and Score 0.64.

On the sealed test, ECE fell from 0.130 to 0.054 without changing argmax accuracy. Operationally, the useful quantity is not “confidence” alone. It is coverage at a threshold together with empirical accuracy on the covered slice.

Serving

Training is only half the system

I benchmarked the actual release runtime using MLX in float16 on the same M5 Pro. Each shape used 1,000 iterations after warmup in one process.

Questions / requestP50P95Peak memory
110.1 ms10.3 ms1.91 GB
535.8 ms36.8 ms2.43 GB

P95/P50 stayed under 1.03 at every tested shape. Predictability matters when a model sits in a synchronous decision path.

Two serving bugs were hiding in plain sight

The release runtime was loading float32 weights because dtype conversion happened before loading instead of after. It also padded inputs to multiples of 16 even on paths that did not benefit from compiled-graph padding. Fixing both brought single-question P50 to 10.1 ms with no prediction changes.

Backend parity

Strict 1e-4 numerical parity holds on CPU. For deployment, numerical parity is useful; decision parity is essential.

Boundary of the design

Where the model still fails—and how I knew the encoder had reached its ceiling

Option-order sensitivity

5.8% of Choice predictions change when options are permuted, against a 5% goal. The explicit invariance objective I tried destabilized optimization, so production should keep option order stable or average across orderings where latency allows.

Fine-grained affect remains weak

Emotion classification and five-level sentiment remain weak because the permissively licensed substitute datasets transferred poorly.

Numeric and multi-step reasoning remain weak

This is the more fundamental limitation. The model struggles when a decision requires comparing multiple numbers, applying multi-step transformations, or reasoning across distant evidence.

The interface itself has limits

context    512 tokens
options    2–10
modality   text only

Several independent signals pointed toward a backbone ceiling: held-out accuracy plateaued while training accuracy kept rising; more epochs did not reliably help; three seeds often agreed on the same wrong answers; numeric comparisons remained weak; and 5.1% of Open-Jev validation states were truncated.

When a larger LLM backbone becomes the better choice

A larger instruction-tuned LLM brings more world knowledge, arithmetic and multi-step reasoning, longer context, and stronger instruction-following priors. It can also be adapted with LoRA or other parameter-efficient methods that reduce representation drift.

But a larger backbone does not require returning to free-form generation. The interface can remain typed question → constrained scores → normalized probabilities.

Prefer a small encoder when

Latency and throughput are critical, inputs are short, outputs are bounded, evidence is local, and calibrated probabilities matter.

↔
Prefer a larger LLM when

World knowledge, numeric reasoning, multi-step reasoning, long context, or highly variable schemas dominate the workload.

What is the smallest backbone that puts enough capability underneath the decision interface for this workload?
What survived 46 runs

What 46 experiments taught me

Data composition beats cleverness surprisingly often

My largest improvement did not come from a new optimizer, a novel loss, more epochs, or an ensemble. It came from putting the right data into the gradient stream in the right proportions.

Full fine-tuning forgets what disappears

If the final model needs a capability, keep showing it examples of that capability. Epoch-level proportions are not enough; inspect what the optimizer actually sees between updates.

Measurement resolution should constrain your claims

How large is the paired uncertainty?
How large is seed variance?
Can the evaluation set actually resolve the improvement?

A small decimal difference in a table is not automatically evidence.

Negative experiments are valuable when they eliminate hypotheses

Sequential training failed. Permutation consistency failed. Hard/soft CE blending failed. NLI transfer failed. Each failure made the search space smaller.

Calibration deserves its own data

For constrained decisions, probabilities influence automation thresholds, review routing, escalation, and trust. Calibration is a modeling stage, not a presentation detail.

Training and inference engineering are part of the same system

A dtype-loading bug or unnecessary padding can erase a meaningful share of the latency advantage created by choosing a smaller architecture.

Open-source work dramatically shortens the learning curve—but does not remove the need to validate assumptions

Almost every part of this project benefited from work other people made public: pretrained backbones, datasets, training recipes, calibration techniques, MLX examples, PyTorch implementations, statistical methods, inference patterns, and benchmark code.

That made it possible for one person with one laptop to explore a problem that would otherwise have required far more infrastructure. But copying a technique because it worked elsewhere was never enough. NLI transfer looked reasonable and hurt the target task. Consistency regularization looked reasonable and collapsed training. Sequential specialization looked reasonable and caused forgetting.

Open-source work gave me a much better starting point. The experiments still had to decide what survived.

Eventually, the backbone becomes the bottleneck

When held-out performance plateaus, training performance keeps improving, multiple seeds make the same mistakes, ensembling does not help, and error analysis identifies systematic reasoning gaps, another optimizer experiment may no longer be the highest-value next step.

Closing thought

Nirnaya-Flash was built by one person, on one personal laptop, largely by learning from open-source work and repeatedly testing which ideas held up on the problem in front of me.

The final model did not come from one magical loss function or hyperparameter. It came from progressively tightening the experimental system around the model.

You can learn a surprising amount with modest hardware when the experiments are designed carefully, the evidence is treated seriously, and you are willing to learn from the open-source work that already exists rather than starting from a blank page.
